## 1. Method

1. **Find before fixing.** An edge-case sweep (`parsers/stability_checks.py`) feeds awkward inputs into the PUBLIC entry point of
   each engine and judges the outcome against what a correct system should do (graceful result, clear refusal, or either).
   It was run **before any change**, from a pristine copy of the Day 56 tree, and the result saved
   (`data/results/day57_edge_sweep_before.json`). My first attempt at that run accidentally executed on the already-fixed code
   (a missing tool broke the command chain and the output said "0 failed"); I caught it, rebuilt the pristine tree and redid it.
2. **Read the root cause** of each failure in the source before changing anything.
3. **Fix narrowly**, keep the default behaviour for valid input, and **pin each fix with a test that names the behaviour before it**.
4. **Prove the tests bite**: each fix was reverted in a scratch copy and the tests had to fail (16 reverts).
5. **Run the sweep again** and the earlier days' demos (Days 53–56) to check nothing else moved.

### Input validation
A `None` interview answer was stored silently; NaN experience fell through to the hardest question tier; an unknown technical domain was a bare
`KeyError: 'cobol'`; a blank job description reached scikit-learn and surfaced "empty vocabulary". All are now refused with a clear message
(`TypeError`/`ValueError`, or a coded API error).

### A regression I introduced and the tests caught
My digit rule (C2) covered "notice_period" but the engine calls that question **"availability"** internally, so a bare "30" became vague
(it had been fine). A regression test caught it before it left the day; the rule now covers both names.

## 3. API stabilization — the four service classes

The four `*/service.py` classes are the project's public API boundary. They were **Day 2 placeholders** that disagreed with the real
engines, and their old tests encoded the placeholders' behaviour:

| Placeholder behaviour | Why it was wrong |
|---|---|
| Decision: its own weights (0.2/0.1/0.25/0.35/0.1) and thresholds | not the Day 41/51/52 logic the rest of the project uses |
| Decision: a missing score counted as **0** (`payload.get(key, 0)`) | a single round of 90 produced **"rejected"** |
| Decision: **automatic "rejected" below 50** on any evidence | contradicts the project rule (Day 52): a rejection is only a recommendation a person confirms, never on incomplete evidence |
| Decision: NaN passed straight through to the output | invalid JSON |
| Screening: `call_status: "answered"`, score 0, for *any* request | no call had happened |
| Interview: a placeholder transcript and scores of 0 | looked like a result |
| ATS: counted keywords | had nothing in common with the real ATS score |

**New contract (`API_VERSION 1.0`).** Use `service.run(payload)`; it never raises and always returns one of two shapes:
```
success: {service, model_version, api_version, status: "success", ...fields}
error:   {service, model_version, api_version, status: "error", error: {code, message, field}}
```
Error codes: `invalid_payload`, `invalid_input`, `missing_field`, `invalid_score`, `too_large`, `unsupported_value`, `internal_error`
(an unexpected exception is logged in full; the caller sees only a generic message). Responses are JSON-safe (NaN/inf → null, enums → values),
deterministic, and size-limited (200,000 characters per text, 200 items per list). `process()` remains for direct callers and raises typed errors.

| Service | Request | Response (key fields) |
|---|---|---|
| ATS | `resume_text`, `job_description` (real engine) *or* `job_requirements` (deprecated keyword mode) | `scoring_mode`, `ats_score`, `zone`, `role_category`, `components[]`, `warnings[]` |
| Screening | `candidate_id`, `turns[{text, confidence, is_silent}]`, `job_role` | `call_status` (`not_started` / `completed` / `ended_early` / `incomplete`), `screening_score` (null if not started), `categories_answered/missing`, `turns_used` |
| Interview | `interview_type` (`hr` / `technical`), `answers[]`, `role_type`, `experience_level`; technical also `domain`, `experience_years` | `interview_status` (`not_started` / `scored`), `hr_score` or `technical_score` (null if not started), `answers_scored/ignored`, `non_substantive_answers`, `tier` |
| Decision | any of `ats_score`, `screening_score`, `hr_interview_score`, `technical_score`, `machine_test_score` (0–100), `role_type`, `experience_level`, `ats_zone`, `candidate_id` | `hiring_fit_score`, `decision` (`selected` / `hold_review` / `rejected`), `hold_kind`, `confidence`, `provisional`, `missing_rounds`, `human_review_required/reasons`, `human_confirmation_required`, `automated_action`, `reasons` |

**Breaking changes for existing callers** (stated, not hidden): Decision `decision` value `hold` → `hold_review`; a partial set of scores is
now `hold_review / pending_evidence`, never `rejected`; `communication_score` is accepted as an alias for `hr_interview_score`;
`behavior_score` is ignored with a warning (no such round); Screening/Interview no longer fabricate an "answered" call or a transcript;
ATS adds `scoring_mode`, `zone`, `components`. The old keyword mode and its numbers are unchanged. The two Day 2 tests in
`tests/test_scoring.py` were rewritten for the new contract with the reason recorded in the file.

**Stability measured, not assumed:** the real ATS score depends on the corpus its vocabulary is fitted on (job-description-only moves a score
by up to 5.5 points; resume + job description moves it by ≤ 0.8 against a 20-document corpus). The API therefore fits on exactly the resume and
job description given, so the same pair always scores the same; pass `matcher=` for a shared batch corpus.

## 6. Still open — not fixed, and why

* **O1 — meaning in technical scoring.** A confidently wrong answer scores within 3 points of a correct paraphrase (42.5 vs 43.5), because the rubric is
  phrase-based. Fixing that needs misconception data or a language model; neither is in the project. Pinned by a characterisation test.
* **O2 — cross-stage claims** (e.g. "8 years" claimed against a resume showing 3, F6) still do not feed the decision. How to weigh them is a product
  decision (block selection? lower confidence? flag only?). `find_inconsistencies` from Day 56 is ready to lift into the aggregator.
* **O3 — machine-test stage** is still outside the simulation, so technical journeys end `pending_evidence`.
* **O4 — duplicated zone logic.** `eligibility_engine` still derives the zone itself (now with the same skill-evidence rule) instead of calling `ats_zone_of`;
  merging them is a small, safe refactor left for review.
* **O5 — nothing is deployed.** No database, key service, login, rate limiting, voice provider or monitoring (Day 55 gaps stand). The services
  validate input and never leak internals, but they are not authenticated.
* **O6 — the sweep is 80 hand-chosen cases.** It proves those pass, not that no other bug exists; the cases were extended once after the
  service placeholders were found. Real traffic will find more.
* **O7 — performance was not re-benchmarked** after the changes; no speed claim is made.
